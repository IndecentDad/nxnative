# Shared iCloud save synchronization (iOS)

The iOS front end always runs a game from its local transactional `Documents/save.work` mount. `nn::fs::Commit` atomically publishes `Documents/save`. The Saves menu snapshots only that committed tree; it never uploads `save.work`, shader libraries, logs, RomFS, caches, or app assets. A snapshot is immutable and contains `save/` plus a manifest with its Switch title ID, content hash, revision UUID, parent revision, and guest filename aliases. The aliases are restored on import if iCloud strips their extended attributes. Cloud path: `<container>/Documents/NXNative/Saves/<TITLE_ID>/<revision>/`. The shared container's Documents folder appears in iCloud Drive/Files after the first document is published on a provisioned device.

Use **Saves** during gameplay for **Sync Now**, **Export Save to Files**, **Import Save from Files**, or **Import Cloud Save on Next Launch**. Sync/export run off the main thread. Imports are verified and staged; fully quit and relaunch to install them before the guest mounts. An import is held if the local save changed after staging. The old committed save is retained under `Library/Application Support/NXNativeSaveSync/ImportedBackups/`. Exports are in `Documents/SaveExports/` and can be copied through Files. Sync status and failures appear briefly on screen and in `Documents/log.txt`. Local play and exports continue when iCloud is unavailable.

Each app tracks its last adopted cloud revision in local Application Support. Sync uploads when only the local save changed, offers import when only the cloud changed, and reports a conflict when both changed or multiple cloud branches appear. It never replaces a cloud revision or silently installs a divergent save. Since iCloud discovery is eventually consistent, two offline devices may publish separate immutable heads; once both appear, sync reports the branch conflict and retains both copies in Files. Choose and export the desired copy before resolving a conflict. Automatic background uploads are intentionally deferred until on-device behavior is measured; Sync Now is the explicit trigger.

## Build and provision

The normal NSP script passes its environment to `dm/ios/tools/build_ipa.sh`. The default bundle ID is stable: `org.nxnative.<lowercase title ID>`. Use the same ID on every rebuild and when installing; changing the display name does not change the save identity. To opt in, set:

```sh
export DM_TEAM_ID=YOUR_TEAM_ID
export DM_ICLOUD_CONTAINER=iCloud.your.reverse.dns.shared.saves
export DM_BASE_ENTITLEMENTS=/path/to/existing-memory-entitlements.plist
export DM_BUILD_VERSION=2.1.1  # numeric and higher than this app's prior build when adding iCloud metadata
```

`DM_BASE_ENTITLEMENTS` is optional, but use it when the game needs existing increased-memory-limit or extended-virtual-addressing entitlements. The existing Dread plist is `/volume1/Media/Roms/iOS/Metroid Dread/Metroid-Dread.entitlements` on Synology; provide an accessible copy on the build Mac. The generator merges reusable capabilities with the three iCloud Documents entitlement keys, strips old app/team identity keys, and refuses conflicting cloud values. `DM_ICLOUD_CONTAINER` is optional; without it the app still has local export/import and the build requests no cloud capability. The generated Xcode project uses `Gen/DmIOS.entitlements`, and its Info.plist gets matching `DMTitleID`, `DMICloudContainer`, and public `NSUbiquitousContainers` metadata. The IPA gets an adjacent `<output.ipa>.entitlements.plist` for inspection/signing. A cloud-enabled build uses an ad hoc binary signature to expose requested entitlements to PlumeImpactor; it still needs device provisioning and signing. The existing memory entitlements are preserved only if supplied through `DM_BASE_ENTITLEMENTS` or restored by the final signer.

In Apple Developer **Certificates, Identifiers & Profiles**, create one shared `iCloud.*` container under the intended team. For each game, register an **explicit App ID** with its stable bundle ID, enable **iCloud Documents**, associate that container, and regenerate a development or distribution provisioning profile for that App ID and device. Confirm the profile allows the requested iCloud and memory entitlements. Do not assume an existing profile or a free Apple ID has these capabilities. Apple's [iCloud configuration guide](https://developer.apple.com/documentation/Xcode/configuring-icloud-services) lists the entitlement keys; [Xcode's container guide](https://help.apple.com/xcode/mac/current/en.lproj/devcae40ccb9.html) explains shared containers; [Apple's document synchronization guide](https://developer.apple.com/documentation/uikit/synchronizing-documents-in-the-icloud-environment) covers public Files metadata and the required bundle-version increase.

PlumeImpactor says it derives requested entitlements from the binary when provisioning. Keep its bundle identifier equal to the explicit App ID, install with the matching team/profile, and inspect the installed signature/profile before trusting sync. If Plume rewrites the bundle ID or drops iCloud/memory entitlements, use a signer that accepts the provided entitlements and matching profile. Confirm `com.apple.developer.icloud-services` contains `CloudDocuments` and both container identifier arrays name the selected container. Apple's [provisioning profile note](https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles) explains the profile allowlist. Test with two devices on the same Apple ID and iCloud Drive enabled. Verify Files visibility, upload/download, offline play, and divergent-edit conflict behavior before using this for valuable saves.

## Development checks

Run `python3 -m unittest discover -s dm/ios/tests -p 'test_*.py'` on the host. On Tahoe, run `dm/ios/tests/check_projects.sh` with `XCODEGEN` set if needed; it generates two small projects without an IPA. Compile `DmSaveSync.m`, `main.m`, and `front_ios.m` against the iOS SDK. Run `dm/ios/tests/save_sync_test.m` as a Foundation command-line test on Tahoe/APFS to exercise clonefile snapshots, interrupted publication, conflicts, offline status, file import, deferred apply, and title isolation. No full game build is needed for these checks.
